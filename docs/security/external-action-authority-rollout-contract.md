# External action authority rollout contract review

This review records the contract for the operator configuration that activates external action-authority verification. It was completed before the runtime implementation on 2026-09-18.

## Decision under review

The verifier remains off by default. When an operator enables it, Pipelock must verify every supplied `Pipelock-Authority` grant. A missing grant is denied only when the request's resolved agent and destination match a configured required scope. A missing grant outside those scopes keeps the current behavior.

This distinction is required for compatibility. `authority.Evaluate` treats an installed verifier as mandatory for every request and returns `malformed_reference` when a request has no authority reference. Installing a plain `LocalVerifier` in the runtime would deny ordinary traffic in every existing deployment.

Outside a required scope, an attacker who omits the header gets today's behavior. That's an intentional rollout mode with opportunistic enforcement of supplied grants, not complete authority enforcement.

## Round 1

1. **STATES.** Production currently has only the nil-verifier state, which preserves existing behavior. The implementation must add and test disabled, enabled with an optional grant, enabled with a matching required scope, and enabled with a non-matching scope. It must also test malformed or unreadable key and revocation files, no issuer keys, empty scopes, and missing agent identity. Reload coverage must include disabled to enabled, enabled to disabled, changed key or revocation data, and an unchanged effective authority configuration. A failed reload must retain the last valid verifier rather than replacing enforcement with nil. Old binaries will reject the new YAML field, so a mixed-version fleet must upgrade all instances before the field is deployed. After a successful request, the reserved header and MCP metadata must still be absent from upstream traffic. Before merge, rebase onto the grant-lifetime change and compare the resulting `internal/authority` content, including schema version 2 and its time reasons, rather than treating a clean rebase as proof.

2. **DIRECTION.** Disabled mode fails compatible because no verifier is installed and existing traffic continues. Enabled mode fails closed for an invalid, malformed, revoked, expired, untrusted, or mismatched supplied grant on every transport. A missing grant in a matching required scope also fails closed. A missing grant outside the scope is allowed by design, which is a known fail-open boundary and must be described as such. Startup or reload can't silently install an unusable verifier. An enabled configuration with missing, unreadable, malformed, or empty trust input must fail. HTTP responses and MCP JSON-RPC blocks must continue to report an authority denial without exposing grant contents. Audit events retain the machine reason. This feature has no dashboard, badge, or API status output today, so implementation mustn't claim one.

3. **BLAST RADIUS.** The shared authority carrier affects fetch, forward HTTP, CONNECT, WebSocket, MCP stdio, MCP HTTP, and MCP WebSocket. `internal/config` owns YAML loading and validation, while `internal/cli/runtime` owns initial construction and reload. `internal/proxy` and `internal/mcp` consume the verifier. The documentation, configuration presets, default values, YAML parser, validation, reload path, and tests must use one field spelling and one scope definition. The offline verifier SDKs, receipt format, playground, and dashboard don't consume this setting. No parity check currently proves those operator surfaces agree, so the implementation needs a config fixture and documentation-accuracy coverage that makes drift fail a test.

4. **SHOULD THIS EXIST, AND ONLY THEN, IS THE APPROACH RIGHT.** This work turns an otherwise unreachable verifier into a safe rollout path. It gives an operator a narrow way to require signed authority without breaking every request that predates the header. It changes the public YAML configuration contract, but it doesn't change the signed grant format, receipt format, wire carrier, or verifier SDK contract. The authority package owns grant semantics, and the current lifetime branch is the authority for schema version 2 integration. A scope-aware verifier wrapper is the correct shape because it makes the missing-reference decision before calling the existing mandatory carrier gate. Modifying `Evaluate` to make missing references globally allow would weaken callers that intentionally install a mandatory verifier. Receipt binding, credential delegation, redirect re-verification, and replay resistance are separate contract decisions and remain out of scope.

5. **CLASS, NOT INSTANCE.** The source search covers every authority consumer: `internal/proxy/authority.go`, `internal/mcp/authority.go`, their transport tests, and `internal/authority/carrier.go`. The new scope policy must be a single authority-package implementation used by both proxy and MCP paths. It mustn't grow separate HTTP and MCP matchers. Notable absences are a runtime configuration block, a scope matcher, a reloadable verifier holder, and any receipt or SDK consumer of configured authority scope.

6. **VACUITY.** No new guard exists in this report-only phase, so there isn't an honest vacuity result yet. Before accepting the implementation, a test will neutralize only the scope guard in a temporary copy under an `EXIT` trap and a shell deadline. The missing-grant-in-required-scope test must then fail. Restoring the guard must make it pass. A test that still passes with the guard neutralized will be reported as vacuous and won't count as evidence.

7. **PREDECESSOR AUDIT.** This is the first round. The predecessor defect is the proposed unconditional runtime `LocalVerifier` installation, and the source confirms it would deny empty references. The next round will attack the new scope wrapper first, especially its absent-reference and reload transitions.

8. **EVIDENCE ORIGIN.** Trust decisions depend on operator-provided issuer-key and revocation files. Pipelock can validate their syntax and load outcome, but it can't independently establish that the operator distributed authentic files. Tests signed by local helpers prove Pipelock's behavior, not an outside issuer's implementation. The implementation must retain conformance vectors for the verifier and add transport tests that carry a real signed fixture through each carrier. A nonexistent or unreadable file causes a startup or reload error. It never creates an empty trusted set.

9. **AVAILABILITY AND OPERABILITY ARE FAILURE DIRECTIONS TOO.** An outage from requiring a grant too broadly would cause operators to disable the feature. Required scopes therefore need exact, validated agent and destination matching, and the guide must show a narrow first scope. Startup errors must name the exact `external_action_authority` field that needs correction. Missing-grant audit and operator messages must name the configured required scope path. Invalid-grant messages must identify authority verification without leaking the opaque grant. The remedy must be a runtime control that reads a trusted issuer key file, revocation file, or required scope. It mustn't suggest relaxing unrelated scanner policy.

10. **HONEST CONVERGENCE.** The first round confirmed the existing compatibility defect and found no additional shipped fail-open path beyond the approved outside-scope omission behavior. The implementation isn't converged yet. A second round must review the scope wrapper, reload publication boundary, all transport wiring, and the vacuity result before completion. This report doesn't claim that replay, redirects, delegation, or receipt binding are solved.
