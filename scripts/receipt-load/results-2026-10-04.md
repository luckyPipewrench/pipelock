# Signed receipt load test, 2026-10-04

## Result

The million request question remains unproven. At concurrency 128, a 2,000 request run measured 152 requests per second with default best effort receipts and 62 requests per second with `require_receipts: true`. A million requests at those rates would take about 1 hour 49 minutes and 4 hours 29 minutes respectively, or more than six hours for the two recorded modes. The run stopped under the task's infeasibility condition. These are projections from the measured pilot, not million request results.

All 2,000 client requests got the intended decision in each mode: 1,900 allowed and 100 blocked by the synthetic DLP case. The best effort run had one matching action receipt per request, plus three session control receipts. The required run had one block receipt and two allow receipts per request, plus three session control receipts. The pinned, whole recorder verifier passed both complete chains after clean shutdown. No missing request receipt or broken chain appeared in this pilot.

## Setup

Source: `origin/main` at `3dae32224255253694ff018732ce8dd033ef90ee`. Binary: `pipelock version 3.6.0-19-g3dae32224`, built with `make build`; Go `go1.27.0-X:nodwarf5`. Host: Linux/amd64, AMD Ryzen 7 7800X3D, 8 physical cores and 16 threads, 61 GiB RAM. The sink and forward proxy used separate ephemeral loopback ports on one machine. The sink returned two bytes for each allowed GET.

Each mode used a fresh `pipelock init --preset balanced` configuration, recorder directory, and generated Ed25519 key. The harness enabled `forward_proxy`, set `fetch_proxy.monitoring.max_requests_per_minute` to 10,000,000, and added only `127.0.0.1/32` to `ssrf.ip_allowlist` so this local sink could be reached. Recording was disabled, enabled with the default best effort setting, or enabled with `require_receipts: true`. Every twentieth URL carried a synthetic GitHub token shape in its query and was blocked by core DLP; all other URLs carried only a unique numeric ID. The sink's response body was `ok`. Requests used one shared Go HTTP client with 128 workers and connection reuse. This measures one local deployment and this request mix, not Internet latency or large response scanning.

The reproducible command is:

```bash
RECEIPT_LOAD_REQUESTS=2000 RECEIPT_LOAD_CONCURRENCY=128 scripts/receipt-load/run.sh "$(work-capture-dir --large)"
```

The default command omits those two environment variables and runs one million requests per mode at concurrency 128. Each invocation needs a new output directory. The command builds the binary, provisions each mode through `pipelock init`, runs the local sink and proxy, saves one-second process samples and raw recorder files, and runs `pipelock verify-receipt --whole-recorder --require-seal --chain DIR --key KEY` after a clean stop.

The last request receipt timestamp preceded the final client response in both recorded runs. The recorder file modification time was 17.5 and 16.6 ms later respectively; that is only an upper bound for the last receipt append because the file also contains the clean shutdown seal. The harness cannot observe the exact append time of one line through the filesystem. The two recorded modes had zero missing request IDs, zero client errors, and zero unexpected HTTP statuses. The local sink counted 1,900, 1,901, and 1,902 GETs across off, best effort, and required runs; the extra one and two were not classified by request ID and should not be treated as a proxy retry finding without another instrumented run.

The final 200 request smoke run at concurrency 20 showed the same decision and verification outcome. It measured 12,838, 151, and 61 requests per second for off, best effort, and required respectively. The similar recorded throughput at concurrency 20 and 128 is why more clients did not make the million request run practical here. The 2,000 request RSS rise can include Go warmup; it does not establish sustained memory growth or a leak.

## Limits

The chain result proves the present 2,000 request recorder files are internally linked, signed by the generated key, and sealed after shutdown. The request ID comparison checks that each client request has an action receipt. It does not prove that a million request chain stays complete, that the recorder never falls behind over hours, or that memory stays bounded over hours. The off run has no chain by design. All traffic and storage were on one host, so these latency numbers should not be applied to remote upstreams or other disks.
